1. Time Complexity

Method A — The Master Theorem

For any divide-and-conquer recurrence of the form:

T(n) = a · T(n/b) + f(n)

a = number of sub-problems      (a ≥ 1)
b = factor the input shrinks by (b > 1)
f(n) = work done OUTSIDE the recursion (divide + combine)

Compute the critical exponent c = logb(a), then compare f(n) against nc:

CaseCompareWho dominatesAnswer
1f(n) < ncthe leaves (recursion) winΘ(nc)
2f(n) = nctie — every level costs the sameΘ(nc log n)
3f(n) > ncthe root (top work) winsΘ(f(n))

Worked Example 1 — Merge Sort

Step 1 — Identify a, b, f(n). Merge Sort splits into 2 halves and merges in linear time → a=2, b=2, f(n)=n. So T(n)=2T(n/2)+n.
Step 2 — Critical exponent. c = log22 = 1, so nc = n1 = n.
Step 3 — Compare. f(n) = n vs nc = n → equal → Case 2.
Step 4 — Conclude. T(n) = Θ(n log n).

Worked Example 2 — Binary Search

Step 1. One sub-problem of half size, constant comparison → a=1, b=2, f(n)=1. T(n)=T(n/2)+1.
Step 2. c = log21 = 0, so nc = n0 = 1.
Step 3. f(n)=1 vs nc=1 → equal → Case 2.
Step 4. T(n) = Θ(log n).

Worked Example 3 — Case 1 (leaves win)

T(n) = 4T(n/2) + n  (e.g., a naive matrix sub-problem split).

Step 1. a=4, b=2, f(n)=n.
Step 2. c = log24 = 2 → nc = n2.
Step 3. f(n)=n < n2 → Case 1 (the recursion dominates).
Step 4. T(n) = Θ(n2).

Worked Example 4 — Case 3 (root wins)

T(n) = 2T(n/2) + n2.

Step 1. a=2, b=2, f(n)=n2.
Step 2. c = log22 = 1 → nc=n.
Step 3. f(n)=n2 > n → Case 3 (top-level work dominates).
Step 4. T(n) = Θ(n2).

Method B — The Recursion Tree

When you want to see why the Master Theorem works (or when it doesn't apply), draw the tree. Rule: sum the work at each level, then sum all levels.

Worked Example 5 — Merge Sort via recursion tree

For T(n) = 2T(n/2) + n, each node is labelled with the combine work it does:

Level 0: n → work = n / \ Level 1: n/2 n/2 → work = n/2 + n/2 = n / \ / \ Level 2: n/4 n/4 n/4 n/4 → work = 4 · (n/4) = n ... ... Level k: (2^k nodes each doing n/2^k work) → work = n ... Leaves: n nodes, each O(1) → work = n
Step 1 — Work per level. Every level sums to exactly n. (Twice as many nodes, each doing half the work → cancels.)
Step 2 — Number of levels. The input halves each level until size 1: that's log2n levels (plus the leaf level).
Step 3 — Total. (work per level) × (number of levels) = n × log n.
Step 4. T(n) = Θ(n log n) — matching the Master Theorem. ✓

Worked Example 6 — Unbalanced tree: T(n) = T(n/3) + T(2n/3) + n

The Master Theorem doesn't apply (uneven split), so the tree is the right tool.

Step 1 — Work per level. At the root: n. Children do n/3 + 2n/3 = n. Every full level still sums to n.
Step 2 — Height. The longest path shrinks by the slowest factor (×2/3 each time). It reaches size 1 after about log3/2n levels.
Step 3 — Total. Upper bound = n per level × log3/2n levels = O(n log n). (Lower bound is similar.)
Step 4. T(n) = Θ(n log n).

2. Space Complexity

Space complexity = extra memory an algorithm needs beyond the input. Count two things:

  1. Auxiliary data structures you allocate (temp arrays, hash maps, output buffers).
  2. Recursion stack depth — each in-flight recursive call keeps a stack frame (its local variables + return address). Max depth = stack space.
⚠️ Key subtlety: it's the maximum depth of the call stack at any one moment, not the total number of calls. Two sibling recursive calls run one-after-another, so only one is on the stack at a time.

Worked Example 7 — Merge Sort space

Aux structures: the merge step needs a temporary array to hold the merged result → up to O(n).
Stack depth: recursion is log n deep → O(log n).
Total: O(n) + O(log n) → dominant term → Space = O(n).

Worked Example 8 — Quick Sort space (in-place)

Aux structures: none — it partitions in place by swapping → O(1).
Stack depth (average): balanced partitions → depth O(log n) → Space = O(log n).
Stack depth (worst): fully unbalanced (sorted input, bad pivot) → depth O(n) → Space = O(n).

Worked Example 9 — Recursive vs iterative sum

# Recursive — O(n) stack depth (n nested calls before any return)
def sum_rec(arr, i):
    if i == len(arr): return 0
    return arr[i] + sum_rec(arr, i+1)

# Iterative — O(1) extra space (one accumulator, reused)
def sum_iter(arr):
    total = 0
    for x in arr: total += x
    return total
Recursive: the call chain sum_rec(0)→sum_rec(1)→…→sum_rec(n) all sit on the stack simultaneously before any returns → O(n) space.
Iterative: one variable reused → O(1) space. Same time, very different memory.
💡 Time vs space trade-off: Memoization/DP speeds up time (avoids recomputation) by spending memory to store results. They often pull in opposite directions.

3. Amortized Cost

Amortized cost = the average cost per operation over a whole sequence, used when a rare operation is expensive but most are cheap. It is NOT probability — it's a guaranteed average over the worst-case sequence.

Method A — Aggregate Method

Formula: amortized cost = (total cost of n operations) / n. Find the total, divide by n.

Worked Example 10 — Dynamic array (doubling) via Aggregate

A list that doubles capacity when full. A normal append is O(1); a resize copies all current elements (O(n)).

Step 1 — Cost of the cheap part. n appends, each costing 1 to write the element → n.
Step 2 — Cost of resizes. Resizes happen at sizes 1, 2, 4, 8, …, n. Copy work = 1+2+4+…+n, a geometric series ≈ 2n.
Step 3 — Total. n (writes) + 2n (copies) = 3n.
Step 4 — Divide. 3n / n = 3 → amortized O(1) per append.
Note: a single append can still cost O(n) (the one that triggers the big copy). Amortized O(1) means that across any sequence, the average is constant.

Method B — Accounting (Banker's) Method

Assign each operation an amortized charge (a made-up price). If the charge > real cost, the surplus is stored as credit on the data structure. If the charge < real cost, stored credit pays the difference. Rule: the credit balance must never go negative. If you can keep it ≥ 0 with a constant charge, that charge IS the amortized cost.

Worked Example 11 — Dynamic array via Accounting

Step 1 — Pick a charge. Charge 3 per append.
Step 2 — Allocate the 3 coins.
• 1 coin pays to insert the new element itself.
• 1 coin is saved on the new element, to later pay to copy itself during the next resize.
• 1 coin is saved to pay to copy one older element that has already "spent" its own saved coin.
Step 3 — Check the invariant at a resize. When the array of size n doubles, every one of the n elements needs to be copied. By the scheme above, each element arrived carrying enough credit to fund its own move → the bank balance never goes negative. ✓
Step 4 — Conclude. Constant charge of 3 suffices → amortized O(1). (Matches the aggregate answer.)

Worked Example 12 — Stack with multipop via Aggregate

Operations: push (cost 1), pop (cost 1), multipop(k) (pops k items, cost = items actually removed).

Step 1 — Key observation. An element can only be popped once, and only after it was pushed.
Step 2 — Bound total pops. Over n operations, total pushes ≤ n, so total pops (across all pop/multipop) ≤ n too.
Step 3 — Total cost. pushes + pops ≤ n + n = 2n.
Step 4 — Divide. 2n/n = 2 → amortized O(1) per operation, even though one multipop can cost O(n).

Worked Example 13 — Stack with multipop via Accounting

Charge: push = 2, pop/multipop = 0.
Allocate: of push's 2 coins, 1 pays the push now; 1 is taped onto the element as a "prepaid pop."
Invariant: when an element is popped (by pop or multipop), its prepaid coin covers the cost → the balance never goes negative.
Conclude: all amortized charges are ≤ 2 = constant → O(1) amortized.

Worked Example 14 — Binary counter increment via Aggregate

Incrementing a k-bit binary counter n times. Cost = number of bits flipped.

Step 1 — How often each bit flips. Bit 0 flips every increment (n times); bit 1 every 2nd (n/2); bit 2 every 4th (n/4); bit i → n/2i times.
Step 2 — Total flips. n + n/2 + n/4 + … < 2n (geometric series).
Step 3 — Divide. < 2n / n = 2 → amortized O(1) per increment, even though one increment (e.g. 0111→1000) flips many bits.

Worked Example 15 — Binary counter via Accounting

Charge: 2 per set-bit-to-1 operation.
Allocate: 1 coin flips the bit 0→1 now; 1 coin is stored on that 1-bit, prepaying its future flip back to 0.
Invariant: each increment sets at most one bit to 1 (the rest of the work is carries that flip 1→0, already prepaid). So each increment's real cost is covered by at most 2 coins.
Conclude: amortized O(1) per increment.
Aggregate vs Accounting — when to use which?
• Aggregate: easiest when you can directly bound the total work of n operations (geometric series, "each element popped once"). Gives one average for all operation types.
• Accounting: better when you want to assign different charges to different operations, or prove an invariant intuitively ("every element carries prepaid credit"). Must verify the balance never goes negative.
