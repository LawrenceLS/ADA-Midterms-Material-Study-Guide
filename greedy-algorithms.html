1. The Core Idea

A greedy algorithm builds a solution one piece at a time, always taking the choice that looks best right now (the "locally optimal" choice), and never going back to reconsider. It's fast and simple — but it's only correct when the local choices happen to add up to a globally optimal answer.

The 2 properties a greedy algorithm needs

PropertyWhat it means
Greedy Choice PropertyA globally optimal solution can be reached by making the locally optimal (greedy) choice at each step. In other words, the greedy choice is always "safe" — it never ruins your chance at the optimum.
Optimal SubstructureAfter you make the greedy choice, what's left is a smaller version of the same problem, and an optimal solution to the whole = greedy choice + optimal solution to the remainder.
⚠️ If either property fails, greedy gives a wrong (sub-optimal) answer. Proving greedy is really about proving the greedy choice property.

2. How to PROVE Greedy Correctness — the Exchange Argument

This is the standard proof technique and the one exams ask for. The structure:

  1. Let G be the greedy solution and OPT be any optimal solution.
  2. Assume (for contradiction) they differ. Find the first place they differ.
  3. Exchange OPT's choice at that point for the greedy choice, and show the result is no worse than OPT (still valid, still optimal).
  4. Repeat the exchange step-by-step until OPT has been transformed into G without ever getting worse. Therefore G is also optimal. ∎
To DISPROVE a greedy algorithm, you don't need a proof — just one counterexample where it produces a worse answer than optimal.

3. Worked Examples

Example 1 — Activity Selection (the classic correct greedy)

Problem: Given activities with start/finish times, select the maximum number that don't overlap.
Greedy rule: repeatedly pick the activity that finishes earliest among those still compatible.

ActivitySelection(activities):
    sort activities by finish time ascending
    selected = [ activities[0] ]
    last_finish = activities[0].finish
    for a in activities[1:]:
        if a.start >= last_finish:      # compatible → greedy choice
            selected.add(a)
            last_finish = a.finish
    return selected
Step 1 — Trace an example. Activities (start,finish): A(1,4), B(3,5), C(0,6), D(5,7), E(5,9), F(8,10). Sorted by finish: A(1,4), B(3,5), C(0,6), D(5,7), E(5,9), F(8,10).
Step 2 — Apply the rule. Pick A (finish 4). Next compatible with start ≥ 4: D(5,7) — pick it (last_finish=7). Next compatible with start ≥ 7: F(8,10) — pick it. Result = {A, D, F} → 3 activities.
Step 3 — Why it's correct (greedy choice property). The earliest-finishing activity leaves the most time free for everything after it. Swapping any optimal solution's first activity for the earliest-finishing one never reduces the count (exchange argument), so the greedy choice is safe.
Step 4 — Optimal substructure. After picking it, the remaining task is "select max activities starting after last_finish" — the same problem, smaller. So greedy builds an optimal solution.
Complexity. Dominated by the sort → O(n log n).

Example 2 — Fractional Knapsack

Problem: A knapsack of capacity W. Items have value and weight; you may take fractions of an item. Maximize total value.
Greedy rule: take items in order of highest value-per-weight ratio, filling as much as fits (take a fraction of the last one).

Step 1 — Example. W=50. Items: (value, weight) = A(60,10), B(100,20), C(120,30). Ratios: A=6, B=5, C=4 per unit weight.
Step 2 — Apply. Take all of A (10kg, value 60). Take all of B (20kg, value 100). Now 20kg left; take 20/30 of C → value 120×(20/30)=80. Total = 240.
Step 3 — Why correct. Any unit of capacity is best spent on the highest available ratio. If an optimal solution used a lower-ratio unit while a higher-ratio unit was still available, swapping them increases value — contradiction. So greedy is optimal.
⚠️ This works ONLY because fractions are allowed. The 0/1 Knapsack (whole items only) is NOT solvable by this greedy — it needs dynamic programming. (See practice Q4.)

Example 3 — Coin Change (when greedy works vs fails)

Greedy rule: repeatedly take the largest coin ≤ remaining amount.

Works: coins {1,5,10,25}, amount 30 → 25+5 = 2 coins = optimal. This coin system is "canonical" so greedy is always optimal.
Fails: coins {1,3,4}, amount 6 → greedy takes 4, then 1+1 = 3 coins. Optimal is 3+3 = 2 coins. One counterexample disproves greedy for this system.
Lesson: greedy's correctness depends entirely on the specific denominations. Always test a potential counterexample.

Example 4 — Full exchange-argument proof (Activity Selection)

Claim: picking the earliest-finishing activity g first is safe.
Proof. Let OPT be an optimal solution and o its earliest-finishing activity. Since g finishes earliest of ALL activities, g.finish ≤ o.finish. Replace o with g in OPT. Every other activity in OPT started after o finished, and since g finishes no later than o, they're all still compatible with g. The swap keeps the same number of activities, so the modified solution is still optimal — and it contains the greedy choice. Repeat on the remainder. ∎

1You're given jobs each with a deadline and taking 1 unit of time; each completed-by-deadline job earns a profit. A greedy schedules jobs by highest profit first, placing each in the latest free slot ≤ its deadline. Trace it on: J1(deadline 2, profit 100), J2(deadline 1, profit 19), J3(deadline 2, profit 27), J4(deadline 1, profit 25), J5(deadline 3, profit 15). Trace

Reveal answer

Sort by profit desc: J1(100,d2), J3(27,d2), J4(25,d1), J2(19,d1), J5(15,d3).

  • J1: latest free slot ≤ 2 → slot 2. Schedule: [_, J1, _]
  • J3: latest free ≤ 2 → slot 1. [J3, J1, _]
  • J4: latest free ≤ 1 → slot 1 taken, no earlier slot → skip.
  • J2: latest free ≤ 1 → taken → skip.
  • J5: latest free ≤ 3 → slot 3. [J3, J1, J5]

Selected J3, J1, J5 → total profit = 27+100+15 = 142. (This greedy IS optimal for job sequencing with deadlines.)

2Prove, with an exchange argument, that for Fractional Knapsack, taking items in order of highest value/weight ratio is optimal. Prove

Reveal answer

Suppose an optimal solution OPT differs from greedy. Then there exist two bits of capacity where OPT puts weight from a lower-ratio item L while a higher-ratio item H is not fully used. Take a small amount δ of capacity: remove δ worth of L and add δ worth of H. Value changes by δ·(ratio_H − ratio_L) > 0 — the total value increases. That contradicts OPT being optimal. So no such swap exists, meaning OPT already fills capacity in highest-ratio-first order — exactly what greedy does. ∎

3A greedy for Activity Selection picks the activity with the earliest start time first. Disprove it with a counterexample. Disprove

Reveal answer

Counterexample — three activities [start,finish]:

  • X = [1, 10] (earliest start, but very long)
  • Y = [2, 4]
  • Z = [5, 8]

Earliest-start greedy picks X first; X spans 1–10 and blocks both Y and Z → selects just 1 activity.

Optimal picks Y[2,4] then Z[5,8] → 2 activities.

One long early-starting activity hogs the timeline. So "earliest start" is NOT optimal — only "earliest finish" is.

4Show that the "highest value/weight ratio first" greedy FAILS for 0/1 Knapsack (whole items only). Disprove

Reveal answer

Capacity W=10. Items (value, weight): A(60,10), B(50,5), C(50,5). Ratios: A=6, B=10, C=10.

Greedy by ratio picks B(w5) then C(w5) → weight 10, value 100... wait, that's actually good here. Use a sharper case:

W=10. Items: A(60, 10) ratio 6; B(100, 6) ratio ≈16.7; C(100, 6) ratio ≈16.7.

Greedy by ratio takes B (w6, v100); C won't fit (needs 6, only 4 left); A won't fit → value 100.

Optimal takes A alone (w10, v... 60) — hmm that's worse. The cleanest classic counterexample: W=10, items A(60,10,ratio6), B(100,20...) — let's use the textbook one: W=50, A(60,10,r6), B(100,20,r5), C(120,30,r4). Greedy takes A+B (w30,v160), then can't fit C (needs 30, only 20 left) → 160. Optimal (0/1) takes B+C (w50, v220). Greedy loses because it can't take a fraction of C to use the leftover space.

Takeaway: 0/1 Knapsack needs dynamic programming, not greedy. The ratio greedy only works when fractions are allowed.

5Given this pseudocode, state the greedy rule and argue whether it correctly minimizes the number of platforms needed so no two trains overlap at a station. Analyze

MinPlatforms(arrivals, departures):
    sort arrivals asc; sort departures asc
    platforms = 0; max_platforms = 0; i = 0; j = 0
    while i < n:
        if arrivals[i] < departures[j]:
            platforms += 1; i += 1
            max_platforms = max(max_platforms, platforms)
        else:
            platforms -= 1; j += 1
    return max_platforms
Reveal answer

Greedy rule: sweep through all arrival/departure events in time order; a platform is needed whenever a train arrives before the next departure, and freed when one departs. Track the running count and its maximum.

Correct? Yes. The answer equals the maximum number of trains present at the same time, which is a hard lower bound (you can't serve k simultaneous trains with fewer than k platforms). The sweep computes exactly that maximum overlap, so it's both necessary and sufficient →

Correct, and optimal. Time O(n log n) (dominated by the two sorts).

6Explain the difference between proving greedy is correct (greedy choice property) and merely showing it gives a good answer on one example. Conceptual

Reveal answer

Showing greedy works on one example proves nothing — a wrong greedy can still be right on many inputs. To prove correctness you must show the greedy choice is safe for every possible input, typically via the exchange argument: take an arbitrary optimal solution and show it can be transformed into the greedy one without losing optimality.

Conversely, to disprove greedy you only need one counterexample where it loses to optimal. Asymmetry: proving requires a general argument; disproving requires a single bad case.
