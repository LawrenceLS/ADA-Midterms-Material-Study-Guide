1. Amortized Cost — The Accounting (Banker's) Method

The idea

Some operations are rarely expensive but usually cheap. The accounting method assigns each operation a made-up price called the amortized charge. When the charge is MORE than the real cost, the leftover is saved as credit stored "on" the data structure. When an operation's real cost is MORE than its charge, we spend the stored credit to cover the difference.

If we can pick charges so that the stored credit never goes negative, then the total charges ≥ total real cost — so the charges are a valid upper bound on the average cost. The charge you picked IS the amortized cost.

The 4-step recipe:
  1. Assign a charge to each operation type (a constant you choose).
  2. Decide where credit is stored — usually "on" specific elements or structure state.
  3. Check the invariant: at every point, is there enough stored credit to pay for the expensive operations when they happen? Prove credit ≥ 0 always.
  4. Conclude: the (constant) charge is the amortized cost per operation.

Worked Example — Dynamic array that doubles

An array doubles capacity when full. A normal append is cheap (write 1 element); a resize copies all current elements (expensive, O(n)).

Step 1 — Assign a charge. Charge 3 coins per append. (We'll justify why 3 works.)
Step 2 — Where does the credit go? Split the 3 coins:
• Coin 1 — pays the real cost of writing the new element right now.
• Coin 2 — saved on the new element itself, to pay to copy itself during the next resize.
• Coin 3 — saved to pay to copy one older element that already spent its own saved coin in a previous resize.
Step 3 — Check the invariant at a resize. Consider an array that just filled up at size n and must double. The last n/2 elements were each appended since the previous resize, so each arrived carrying coins 2 and 3. Those saved coins are exactly enough to pay to move all n elements (the n/2 newest pay for themselves AND for the n/2 older ones). Credit never goes negative. ✓
Step 4 — Conclude. A constant charge of 3 covers everything → amortized O(1) per append.
Compare with the aggregate method, which got the same answer by summing n + 2n = 3n total and dividing by n = 3. Accounting gives the same 3, but via a "prepaid credit" story that's easier to extend to trickier structures.

Second Worked Example — Stack with multipop

Operations: push (cost 1), multipop(k) (pops up to k items, cost = items actually popped).

Step 1 — Charge. push = 2, multipop = 0.
Step 2 — Store credit. Of push's 2 coins, 1 pays the push now; 1 is taped onto the pushed element as a "prepaid pop."
Step 3 — Invariant. Every element on the stack carries 1 prepaid coin. When multipop removes it, that coin pays for the pop → charge of 0 for multipop is fine, credit never negative.
Step 4 — Conclude. Max charge is 2 (constant) → amortized O(1) per operation, even though one multipop can really cost O(n).

2. Time Complexity — The Recursion Tree Method

The idea

A recursion tree makes a recurrence visual. Each node represents one call and is labelled with the work that call does outside its own recursive calls (the f(n) part). You then: sum the work on each level, then sum across all levels. This both solves the recurrence and shows you why the answer is what it is.

The 5-step recipe:
  1. Draw the root with its non-recursive work f(n).
  2. Branch: a node of size n spawns a children, each of size n/b.
  3. Work per level: at level i there are aⁱ nodes, each doing f(n/bⁱ) work → multiply.
  4. Count levels: the size shrinks by b each level until it hits the base case → about log_b(n) levels.
  5. Sum the per-level work across all levels (watch whether it's constant, increasing, or decreasing — that's which term dominates).

Worked Example — T(n) = 2T(n/2) + n (Merge Sort)

Level 0: n → 1 node × n = n / \ Level 1: n/2 n/2 → 2 nodes × n/2 = n / \ / \ Level 2: n/4 n/4 n/4 n/4 → 4 nodes × n/4 = n ... Level i: 2^i nodes × n/2^i = n ... Leaves: n nodes × O(1) = n
Step 1–3 — Work per level. At level i: 2ⁱ nodes, each doing n/2ⁱ work → product = n. Every level sums to exactly n (the 2ⁱ and 1/2ⁱ cancel).
Step 4 — Levels. Size goes n → n/2 → n/4 → … → 1: that's log₂n levels.
Step 5 — Sum. n per level × log₂n levels = n log n.
Answer. T(n) = Θ(n log n).

Second Worked Example — T(n) = 3T(n/4) + n (work shrinks per level)

Work per level. Level i: 3ⁱ nodes × n/4ⁱ work = n·(3/4)ⁱ. This decreases geometrically as i grows.
Levels. Shrinking by 4 each time → log₄n levels.
Sum. n · Σ(3/4)ⁱ. A decreasing geometric series is dominated by its first term, so the sum is n · (constant) = O(n). The root dominates.
Answer. T(n) = Θ(n). (Matches Master Theorem Case 3.)
💡 Pattern recognition: if per-level work is constant → multiply by #levels (Θ(n log n) style). If it decreases → the root/top dominates (Θ(f(n))). If it increases → the leaves/bottom dominate (Θ(n^(log_b a))).

3. Randomized — Linearity of Expectation

The idea

Expected value is a weighted average: E[X] = Σ (value × probability). Computing it directly is often painful. Linearity of expectation is the escape hatch:

E[X₁ + X₂ + … + Xₙ] = E[X₁] + E[X₂] + … + E[Xₙ]

This is true ALWAYS — even when the variables are dependent on each other. That's what makes it magical: you break a scary total into tiny, easy pieces, compute each piece's expectation separately, and add.

The 4-step recipe (indicator-variable trick):
  1. Define the total you care about as a sum: X = X₁ + X₂ + …
  2. Make each Xᵢ an indicator: Xᵢ = 1 if event i happens, 0 otherwise.
  3. Find E[Xᵢ]. For an indicator, E[Xᵢ] = Pr[event i happens] (because 1·p + 0·(1−p) = p).
  4. Add them up: E[X] = Σ Pr[event i]. Done — no dependency worries.

Worked Example — Hat check problem

Problem: n people throw their hats in a pile and each grabs a random hat (a uniformly random permutation). What is the expected number of people who get their OWN hat back?

Step 1 — Define the total. Let X = number of people who get their own hat. Write X = X₁ + X₂ + … + Xₙ.
Step 2 — Indicators. Xᵢ = 1 if person i gets their own hat, else 0.
Step 3 — E[Xᵢ]. Person i is equally likely to get any of the n hats, so Pr[own hat] = 1/n. Therefore E[Xᵢ] = 1/n.
Step 4 — Add. E[X] = Σ (1/n) = n × (1/n) = 1.
Beautiful result: no matter how many people, on average exactly 1 gets their own hat. Note the Xᵢ are NOT independent (if n−1 people get their own hat, the last one must too) — but linearity doesn't care. That's the whole point.

Second Worked Example — Expected comparisons / "number of heads"

Problem: Flip a biased coin (heads probability p) n times. Expected number of heads?

Step 1. X = X₁ + … + Xₙ where Xᵢ=1 if flip i is heads.
Step 2–3. E[Xᵢ] = Pr[heads] = p.
Step 4. E[X] = n·p. (For a fair coin p=1/2 → n/2 heads, as expected.) E = np

4. Randomized — Geometric Distribution

The idea

You repeat an independent trial that succeeds with probability p each time, and you stop at the first success. The number of trials until (and including) that first success follows a geometric distribution. The headline fact:

E[number of trials until first success] = 1 / p

Intuition: if something works 1 time in p, you expect to wait 1/p tries. (Success 1-in-6 → expect 6 tries.)

The 3-step recipe:
  1. Identify the trial and its success probability p (per attempt, independent).
  2. Confirm you're counting trials-until-first-success (that's what geometric measures).
  3. Apply E = 1/p. (If you also need the probability of exactly k trials, it's (1−p)^(k−1)·p.)

Worked Example — Coin flips until heads

Step 1. Trial = one coin flip; success = heads; p = 1/2.
Step 2. We want the number of flips until the first heads → geometric.
Step 3. E = 1/p = 1/(1/2) = 2 flips.
Verify by the full formula. E = Σ k·(1/2)^(k−1)·(1/2) = 1·½ + 2·¼ + 3·⅛ + … = 2. ✓

Second Worked Example — Rolling until a 6

Step 1. Trial = one die roll; success = rolling a 6; p = 1/6.
Step 2–3. E = 1/p = 1/(1/6) = 6 rolls.

Why this matters for algorithms

Many randomized algorithms retry a random attempt until it succeeds: e.g. keep picking a random pivot until the split is "good enough," or re-hash until no collision. If each attempt succeeds with constant probability p ≥ ½, the expected number of retries is 1/p ≤ 2 — a small constant. That constant number of cheap retries is exactly why such algorithms are fast in expectation.

5. Practice Questions

1Accounting: A dynamic array that doubles also supports pop (remove last element, cost 1). Using the accounting method, what constant charge per append covers both appends and the resize copies? Accounting

Reveal answer

Charge 3 per append (pop is charge 1, which equals its real cost, so it needs no credit). Allocation: 1 coin writes the element; 2 coins are saved on the element to prepay its own future copy and one older element's copy during the next doubling.

Invariant: each of the newest n/2 elements carries 2 saved coins → enough to move all n elements at a resize. Credit never negative.

Amortized O(1) per operation.

2Accounting: A binary counter increment flips bits (costly carries). Assign a charge per "set a bit to 1" so increments are amortized O(1), and state where credit is stored. Accounting

Reveal answer

Charge 2 each time a bit is set 0→1: 1 coin does the set now; 1 coin is stored on that 1-bit, prepaying its eventual flip back to 0.

Invariant: every 1-bit carries exactly 1 saved coin. An increment sets at most one bit to 1 (the rest of the work is carries flipping 1→0, already prepaid). So each increment costs ≤ 2 charged coins.

Amortized O(1) per increment.

3Recursion tree: Solve T(n) = 2T(n/2) + n² by drawing the tree. State whether root, middle, or leaves dominate. Recursion Tree

Reveal answer

Work at level i: 2ⁱ nodes × (n/2ⁱ)² = 2ⁱ · n²/4ⁱ = n²·(1/2)ⁱ. This decreases geometrically.

Sum: n² · Σ(1/2)ⁱ = n² · (constant ≤ 2) = Θ(n²). The root dominates (the top level's n² swamps everything below).

T(n) = Θ(n²).

4Recursion tree: Solve T(n) = 4T(n/2) + n. Which part dominates? Recursion Tree

Reveal answer

Work at level i: 4ⁱ nodes × n/2ⁱ = n·2ⁱ. This increases geometrically → dominated by the last level (the leaves).

Number of levels: log₂n. At the leaf level i = log₂n, work = n·2^(log₂n) = n·n = n².

T(n) = Θ(n²)

— the leaves dominate. (Matches Master Theorem Case 1: c = log₂4 = 2.)

5Linearity: Roll n fair dice. What is the expected sum of all the faces? Linearity

Reveal answer

X = X₁+…+Xₙ, where Xᵢ is the face of die i. E[Xᵢ] = 3.5 (expected value of one fair die).

By linearity: E[X] = n × 3.5 = 3.5n. No need to consider the (huge) joint distribution of all dice.

6Linearity: In a random permutation of 1..n, an "ascent" is a position i where element i < element i+1. There are n−1 adjacent pairs. Expected number of ascents? Linearity

Reveal answer

Let Xᵢ = 1 if position i is an ascent, for i = 1..n−1. For any adjacent pair, the two values are equally likely to be in increasing or decreasing order → Pr[ascent] = 1/2, so E[Xᵢ] = 1/2.

By linearity: E[total] = (n−1) × 1/2 = (n−1)/2.

7Geometric: A randomized algorithm picks a random pivot; the split is "good" with probability 1/2. What is the expected number of pivot picks until a good split? Geometric

Reveal answer

Trial = one pivot pick; success = good split; p = 1/2. Geometric → E = 1/p = 2.

Expected 2 picks.

A constant, which is why injecting this retry doesn't change the asymptotic running time.

8Geometric: A hash insertion collides with probability 1/4 and must retry. Expected number of attempts to place one key? And the probability it takes exactly 3 attempts? Geometric

Reveal answer

Success = no collision, p = 1 − 1/4 = 3/4.

Expected attempts: E = 1/p = 1/(3/4) = 4/3 ≈ 1.33 attempts.

Exactly 3 attempts: fail, fail, succeed = (1/4)·(1/4)·(3/4) = 3/64 ≈ 0.047 (using (1−p)^(k−1)·p with k=3).
