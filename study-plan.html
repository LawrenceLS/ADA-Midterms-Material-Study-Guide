0. Foundation: Big-O Notation

Big-O describes how fast the number of operations (or memory) grows as input size n grows. We ignore constants and keep only the dominant term.

Best → Worst: O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)

NotationNameMeaningExample
O(1)ConstantSame work regardless of sizeAccess array[5]
O(log n)LogarithmicHalves the problem each stepBinary search
O(n)LinearOne pass through the dataFind max in a list
O(n log n)LinearithmicEfficient sortingMerge Sort, Quick Sort (avg)
O(n²)QuadraticNested loopsBubble Sort
O(2ⁿ)ExponentialDoubles per added itemNaive Fibonacci
O(n!)FactorialTries all orderingsBrute-force TSP
Simplification rules:
• Drop constants: O(2n) → O(n)
• Drop smaller terms: O(n² + n) → O(n²)
• Multiply nested loops: loop inside loop = O(n) × O(n) = O(n²)

Reading the graph: steeper curve = worse. O(1) is flat (best); O(2ˣ) and O(n!) shoot straight up (worst). To "estimate using the O-notation graph," match your operation count to the matching curve.

Topic 1 — Divide and Conquer (Time + Space Complexity)

What it is

A 3-step strategy: Divide the problem into smaller sub-problems → Conquer each recursively → Combine the answers. Examples: Merge Sort, Quick Sort, Binary Search.

Computing TIME — Recurrence + Master Theorem

When an algorithm calls itself, write a recurrence:

T(n) = a · T(n/b) + f(n)
  • a = number of sub-problems created
  • n/b = size of each sub-problem
  • f(n) = work to divide + combine (outside recursion)

Let c = logb(a). Compare f(n) with nc:

CaseConditionResult
1f(n) grows slower than ncO(nc)
2f(n) ≈ ncO(nc · log n)
3f(n) grows faster than ncO(f(n))

Worked Example A — Merge Sort

MergeSort(A):
    if length(A) <= 1: return A
    mid = length(A) / 2
    left  = MergeSort(A[0..mid])     # 1 sub-problem, size n/2
    right = MergeSort(A[mid..end])   # 1 sub-problem, size n/2
    return Merge(left, right)        # merge = O(n)

Split into 2 halves → a=2, b=2; merge is O(n) → f(n)=n.
T(n) = 2T(n/2) + O(n), c = log22 = 1, nc = n. f(n)=n=n¹ → Case 2 → Time = O(n log n).

Space: temp array of size n → O(n), plus recursion stack O(log n). Dominant → Space = O(n).

Worked Example B — Binary Search

BinarySearch(A, target, low, high):
    if low > high: return NOT_FOUND
    mid = (low + high) / 2
    if A[mid] == target: return mid
    if A[mid] < target: return BinarySearch(A, target, mid+1, high)
    else:               return BinarySearch(A, target, low, mid-1)

a=1 (one sub-problem), b=2 (half), f(n)=O(1).
T(n)=T(n/2)+O(1), c=log21=0, n0=1. f(n)=1 → Case 2 → Time = O(log n).
Space: recursive = O(log n) stack; iterative = O(1).

Thinking about SPACE complexity

Space = extra memory beyond the input. Count: (1) extra data structures you allocate, (2) recursion stack depth (each call = one stack frame).

3Merge Sort uses O(n) extra space. Explain how an in-place sort like Quick Sort differs, and state Quick Sort's space complexity (average + worst). Space comparison

▸ Show worked solution

Merge Sort must allocate a temporary array of size n to merge the two halves → O(n) extra memory (it cannot merge in place efficiently).

Quick Sort partitions the array in place by swapping elements around the pivot — it needs no extra array. Its only extra memory is the recursion stack.

  • Average case: balanced partitions → recursion depth O(log n) → Space = O(log n).
  • Worst case: unbalanced partitions (e.g., sorted input with a bad pivot) → recursion depth O(n) → Space = O(n).

So Quick Sort is more memory-efficient than Merge Sort on average, which is one reason it's often preferred in practice.

Topic 2 — Amortized Analysis (Operations per execution)

The idea

When one operation is occasionally expensive but usually cheap, judging by the worst single operation is misleading. Amortized analysis finds the average cost per operation across a whole sequence (no probability — we spread the rare cost over the cheap ones).

💡 Analogy: A $600/year gym membership looks huge as one payment, but amortized over 365 days it's ~$1.64/day.

Three methods

  • Aggregate: total cost of n operations ÷ n. (Easiest — use this.)
  • Accounting (banker's): overcharge cheap ops to bank "credit" for future expensive ones.
  • Potential: define a potential function Φ that stores "energy" before expensive ops.

Worked Example — Dynamic Array that doubles

Appending is usually O(1), but when the array is full you copy all elements to a new array (O(n)). What's the amortized cost per append?

Inserting n items, the array doubles at sizes 1, 2, 4, 8, …, n. Copy costs sum to a geometric series:

copies = 1 + 2 + 4 + ... + n ≈ 2n
total = n (inserts) + 2n (copies) = 3n
amortized = 3n / n = 3 = O(1)

Even though one append can cost O(n), the amortized cost is O(1) per operation.

🎯 Practice Questions — Topic 2

1A stack supports push (cost 1) and multipop(k) (cost = items actually popped). Using the aggregate method, show a sequence of n operations costs O(n) total. Aggregate

▸ Show worked solution

Key insight: an element can only be popped once, and it must have been pushed before it can be popped. So the total number of pops can never exceed the total number of pushes.

  • Total pushes over n operations ≤ n (each push is one operation).
  • Therefore total pops (across all multipop calls) ≤ n as well.
  • Total work = pushes + pops ≤ n + n = 2n.

Amortized per operation = 2n / n = 2 = O(1). Even though a single multipop can cost up to O(n), it can only be that expensive if many cheap pushes happened earlier to "fund" it.

2A binary counter is incremented n times. Show the amortized cost per increment is O(1). Aggregate

▸ Show worked solution

An increment flips bits because of carries. The trick is to count how often each bit position flips over n increments:

  • Bit 0 (ones place) flips every increment → n times
  • Bit 1 flips every 2nd increment → n/2 times
  • Bit 2 flips every 4th increment → n/4 times
  • Bit i flips → n/2i times

Total flips = n + n/2 + n/4 + n/8 + … < 2n (geometric series).

Amortized per increment = 2n / n = 2 = O(1). Although one increment like 0111→1000 flips 4 bits, those costly carries are rare.

3Explain the difference between worst-case cost of a single operation and amortized cost, using the dynamic array. Concept

▸ Show worked solution

Worst-case single operation: The single most expensive append is the one that triggers a resize when the array is full — it copies all n existing elements, costing O(n). If you only looked at this, you'd wrongly conclude append is "slow."

Amortized cost: Looks at the whole sequence. That expensive O(n) resize happens rarely (only when the array doubles), and it's "paid for" by the many cheap O(1) appends before it. Averaged across all operations, each append costs O(1).

In short: worst-case = the single most expensive moment; amortized = the realistic average per operation over a long run. For a dynamic array: worst-case single append = O(n), amortized append = O(1).

Topic 3 — Randomized Algorithms (Expected Running Time)

The idea

An algorithm that makes random choices during execution, so no specific input can force the worst case. Running time becomes an expectation (average over the random choices).

Expected value formula: E[X] = Σ (value × probability). Example: a fair die, E = (1+2+3+4+5+6)/6 = 3.5.

Worked Example — Randomized Quick Sort

QuickSort(A):
    if length(A) <= 1: return A
    pivot = A[ RANDOM index ]        # <-- randomization
    left  = elements < pivot
    right = elements > pivot
    return QuickSort(left) + [pivot] + QuickSort(right)

With a fixed pivot (always first element), a sorted input gives the worst case O(n²) — every partition is lopsided (n-1 and 0). A random pivot means no input can reliably force this.

A random pivot gives a reasonably balanced split with high probability → O(n) work per level × O(log n) levels = Expected time O(n log n). Worst case O(n²) still exists but is astronomically unlikely.

On the O-graph: point to the O(n log n) curve for expected; note O(n²) above it as the unlikely worst case.

"Modify and prove" — what the exam wants

  1. Modify: inject a random choice into a deterministic algorithm (e.g., random pivot).
  2. Prove: write E[T(n)] and show it equals O(n log n).
  3. Estimate: match it to the correct curve on the graph.

🎯 Practice Questions — Topic 3

1Explain why deterministic Quick Sort (pivot = first element) is O(n²) on a sorted array, and how a random pivot fixes it. Reasoning

▸ Show worked solution

Sorted input, pivot = first element (say array [1,2,3,4,5], pivot = 1):

  • Everything is bigger than 1, so left = [] (empty), right = [2,3,4,5]. The split is n-1 and 0 — totally unbalanced.
  • Next level: pivot = 2, left = [], right = [3,4,5]. Same lopsided split again.
  • This recurses n times, and each level does O(n) partition work → n × n = O(n²).
  • Recurrence: T(n) = T(n-1) + O(n) = O(n²).

Random pivot fix: Now the pivot is a random element, so on average it lands near the middle. Expected split ≈ half and half (even a 1/4 : 3/4 split keeps depth logarithmic). The adversary can't design an input to force lopsided splits because the pivot choice is random, not positional. → Expected O(n log n).

2Write the recurrence for the expected running time of randomized Quick Sort and argue why it solves to O(n log n). Proof

▸ Show worked solution

With a random pivot, the expected split is balanced, so on average each of the two sub-problems has about half the elements:

E[T(n)] = 2 · E[T(n/2)] + O(n)

This is exactly the Merge Sort recurrence. Applying the Master Theorem: a=2, b=2, f(n)=O(n), c = log₂2 = 1, f(n)=n=n¹ → Case 2 → O(n log n).

Intuition why it holds even when splits aren't exactly half: a random pivot gives a split at least as balanced as 1/4 : 3/4 with probability ≥ 1/2. A 1/4:3/4 split still shrinks the problem by a constant factor each level, so the recursion depth stays O(log n), and with O(n) work per level the total expected work is O(n log n).

3Flip a fair coin until you get HEADS. Compute the expected number of flips, then connect this idea to randomized-algorithm analysis. Expected value

▸ Show worked solution

This is a geometric distribution: success probability per flip is p = 1/2. The expected number of trials until the first success is 1/p.

E[flips] = 1 / p = 1 / (1/2) = 2 flips

Verification by the formula E[X] = Σ (value × probability):

E = 1·(1/2) + 2·(1/4) + 3·(1/8) + 4·(1/16) + ... = 2

(The weighted sum of k · (1/2)ᵏ converges to 2.)

Connection: Many randomized algorithms repeat a random trial until they "succeed" (e.g., keep picking a random pivot until you get a good-enough split, or retry a random hash). The expected number of trials is 1/p where p is the success probability per trial. If p is a constant (like ≥ 1/2), the expected number of retries is a small constant — which is why randomized algorithms are fast in expectation.

Topic 4 — Greedy Algorithms (Prove correctness from pseudocode)

The idea

At each step, make the choice that looks best right now (locally optimal) and never reconsider. Hope these local choices build a globally optimal solution. Examples: Activity Selection, Huffman Coding, Dijkstra, Kruskal/Prim.

Greedy is correct only if BOTH properties hold

  1. Greedy Choice Property — a global optimum can be reached by making the local best choice at each step (the greedy choice is "safe").
  2. Optimal Substructure — after the greedy choice, the remaining problem is a smaller version of the same problem, and whole optimum = greedy choice + optimum of the rest.

Proof technique — the Exchange Argument

  1. Assume an optimal solution OPT differs from the greedy solution G.
  2. Find the first place they differ.
  3. Exchange OPT's choice there for the greedy choice — show it doesn't make OPT worse.
  4. Repeat until OPT becomes G. Therefore G is also optimal. ∎

Worked Example — Activity Selection

Select the maximum number of non-overlapping activities. Greedy rule: always pick the activity that finishes earliest among compatible ones.

ActivitySelection(activities):
    sort activities by finish time (ascending)
    selected = [ first activity ]
    last_finish = activities[0].finish
    for each activity a in order:
        if a.start >= last_finish:     # compatible = greedy choice
            selected.add(a)
            last_finish = a.finish
    return selected
Worked Example — when greedy FAILS: Coins {1, 3, 4}, make amount 6.
• Greedy: take 4 → remaining 2 → take 1,1 → 3 coins (4+1+1)
• Optimal: 3 + 3 → 2 coins
One counterexample disproves greedy!

🎯 Practice Questions — Topic 4

1For US coins {1,5,10,25} with "always take the largest coin ≤ remaining," argue whether greedy is optimal. Then show it FAILS for {1,3,4}. Prove / Disprove

▸ Show worked solution

US coins {1,5,10,25} — greedy IS optimal. This coin system is "canonical": each larger coin is worth enough that using it never forces you into using more small coins than an optimal solution would. For example, making 30: greedy = 25+5 = 2 coins, which is optimal. There is no amount where greedy uses more coins than necessary, because the denominations are structured so the greedy choice is always safe. (A full proof shows that for any amount, using fewer of a larger coin would require making up the difference with strictly more smaller coins.)

{1,3,4} — greedy FAILS. Counterexample: amount = 6.

  • Greedy: largest ≤ 6 is 4 → remaining 2 → 1+1 → total 3 coins (4+1+1).
  • Optimal: 3+3 → 2 coins.

Since one counterexample exists, greedy is not optimal for {1,3,4}. Lesson: greedy's correctness depends entirely on the specific denominations.

2A "greedy" activity selection picks the shortest-duration activity first (instead of earliest finish). Prove it's incorrect with a counterexample. Disprove

▸ Show worked solution

Consider 3 activities (as [start, finish] intervals):

  • A = [1, 5]   (duration 4)
  • B = [4, 6]   (duration 2, the shortest)
  • C = [6, 10]   (duration 4)

Shortest-duration greedy picks B first (duration 2). But B = [4,6] overlaps both A (ends at 5 > 4) and C (starts at 6, B ends at 6 — if we require strict non-overlap, B blocks A; even sharing endpoints, B conflicts with A). After picking B, neither A nor C can both fit cleanly around it → it selects just 1 activity (B).

Optimal picks A = [1,5] then C = [6,10], which don't overlap → 2 activities.

The single short activity B sits in the middle and blocks two longer, mutually-compatible activities. Therefore "shortest duration first" is not optimal — only "earliest finish time" is provably correct.

3Explain the exchange argument, then use it to prove the "earliest finish time" greedy choice for Activity Selection is safe. Proof

▸ Show worked solution

Exchange argument in plain words: To prove a greedy choice is safe, take any optimal solution, find where it disagrees with greedy, and swap in the greedy choice. If the solution stays just as good after the swap, then greedy's choice was never a mistake — so greedy can reach an optimal solution too.

Proof for Activity Selection:

  1. Let g be the activity that finishes earliest (greedy's first pick). Let OPT be any optimal solution, and let o be the first activity in OPT (the one that finishes earliest within OPT).
  2. Because g finishes earliest of ALL activities, its finish time ≤ o's finish time.
  3. Now replace o with g in OPT. Every other activity in OPT started after o finished, and since g finishes no later than o, all those activities are still compatible with g. So the swapped solution is still valid.
  4. The swap didn't remove any activity — the count is unchanged — so the new solution is still optimal and it now contains the greedy choice g.
  5. Repeat this argument on the remaining sub-problem. Each step shows greedy's choice is safe, so greedy builds an optimal solution. ∎

Conclusion: picking the earliest-finishing activity is always safe because it frees up the most remaining time for future activities.
