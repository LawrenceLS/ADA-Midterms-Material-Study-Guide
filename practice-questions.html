1. Time Complexity

1Solve T(n) = 2T(n/2) + n² using the Master Theorem. Master

Reveal answer

a=2, b=2, f(n)=n². Critical exponent c = log₂2 = 1 → nᶜ = n.

Compare: f(n)=n² grows faster than n → Case 3 (root dominates).

T(n) = Θ(n²).

2Solve T(n) = 9T(n/3) + n using the Master Theorem. Master

Reveal answer

a=9, b=3, f(n)=n. c = log₃9 = 2 → nᶜ = n².

Compare: f(n)=n < n² → Case 1 (leaves dominate).

T(n) = Θ(n²).

3Solve T(n) = 3T(n/4) + n using the Master Theorem. Master

Reveal answer

a=3, b=4, f(n)=n. c = log₄3 ≈ 0.79 → nᶜ ≈ n^0.79.

Compare: f(n)=n = n¹ grows faster than n^0.79 → Case 3 (root dominates).

T(n) = Θ(n).

Clue: when in doubt, remember n¹ vs n^0.79 — the bigger exponent wins.

4Solve T(n) = 2T(n/2) + n log n. (Careful — this is a Master Theorem edge case.) Master

Reveal answer

a=2, b=2 → c=1, nᶜ = n. Here f(n)=n log n, which is slightly larger than n but NOT by a polynomial factor (only by a log). The three simple cases don't cleanly apply.

Use the recursion tree instead: each level sums to n log n-ish... more precisely, level i contributes n·log(n/2ⁱ), and summing over log n levels gives:

T(n) = Θ(n log² n).

Lesson: when f(n) beats nᶜ only by a logarithmic factor, the Master Theorem (basic form) doesn't apply — drop to a recursion tree.

5Use a recursion tree to solve T(n) = 3T(n/2) + n. Recursion Tree

Reveal answer

Work per level: root = n; level 1 = 3·(n/2) = (3/2)n; level 2 = 9·(n/4) = (9/4)n; level i = (3/2)ⁱ · n. The work grows each level.

Number of levels: log₂n.

Total: geometric series n · Σ(3/2)ⁱ dominated by its last term at level log₂n: (3/2)^(log₂n) · n = n^(log₂3).

T(n) = Θ(n^(log₂3)) ≈ Θ(n^1.585).

Check with Master Theorem: c=log₂3≈1.585, f(n)=n < n^1.585 → Case 1 → Θ(n^1.585). ✓ (This is the Karatsuba multiplication recurrence!)

6Analyse the time complexity of this code. Loops

for i in range(n):          # outer
    j = 1
    while j < n:
        j = j * 2            # j doubles
Reveal answer

Outer loop runs n times. Inner while: j doubles (1→2→4→…→n), so it runs log₂n times.

Total = n × log n.

Time = Θ(n log n).

2. Space Complexity

7What is the space complexity of this function, and why? Recursion stack

def factorial(n):
    if n <= 1: return 1
    return n * factorial(n - 1)
Reveal answer

No auxiliary data structures. The recursion chain factorial(n)→factorial(n-1)→…→factorial(1) is n calls deep, and all are on the stack before any returns.

Space = O(n)

(from the call stack). Time is also O(n).

8Compare the space of these two "contains duplicate" approaches. Aux structures

# A: sort then scan neighbours
def has_dup_A(arr):
    arr.sort()
    for i in range(1, len(arr)):
        if arr[i] == arr[i-1]: return True
    return False

# B: hash set
def has_dup_B(arr):
    seen = set()
    for x in arr:
        if x in seen: return True
        seen.add(x)
    return False
Reveal answer

A: sorts in place (ignoring sort's internal stack) and uses O(1) extra for the scan → O(1) auxiliary (but O(n log n) time).

B: the seen set can hold up to n elements → O(n) auxiliary (but O(n) time).

Classic time-space trade-off: B is faster (O(n) vs O(n log n)) but uses more memory.

9What's the space complexity of building and returning a list of the first n squares? Output

def squares(n):
    result = []
    for i in range(n):
        result.append(i*i)
    return result
Reveal answer

The result list grows to hold n numbers.

Space = O(n).

Subtlety: if the question asks for auxiliary space and the output doesn't count, some courses still call this O(n) because the list is explicitly allocated. State your assumption.

10This recursive Fibonacci has exponential time. What is its space complexity? Tricky

def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)
Reveal answer

Time is O(2ⁿ) (huge). But space is only the maximum stack depth at any instant — not the total number of calls.

The deepest chain is fib(n)→fib(n-1)→fib(n-2)→…→fib(1), which is n deep. The two recursive calls happen one after the other, so only one branch is on the stack at a time.

Space = O(n).

Key insight: exponential time, but only linear space. Time ≠ space.

3. Amortized Cost

11A dynamic array triples (×3) in size when full, instead of doubling. Use the aggregate method to find the amortized cost of append. Aggregate

Reveal answer

Resizes happen at sizes 1, 3, 9, …, n. Copy work = 1 + 3 + 9 + … + n, a geometric series with ratio 3, which sums to (3n−1)/2 ≈ 1.5n.

Total = n (writes) + 1.5n (copies) = 2.5n. Divide by n → 2.5.

Amortized O(1) per append.

Any growth factor > 1 (×2, ×3, ×1.5…) gives amortized O(1); the constant just changes.

12Use the accounting method to prove append on a doubling array is O(1) amortized. State the charge and the invariant. Accounting

Reveal answer

Charge: 3 coins per append.

Allocation: 1 coin inserts the new element; 1 coin is stored on the new element (to pay to move itself at the next resize); 1 coin pays to move one already-existing element that has spent its own coin.

Invariant: right before a resize of a full array of size n, exactly the n/2 newest elements carry stored credit — enough to move all n elements. Balance never goes negative.

Constant charge of 3 → amortized O(1).

13A queue is implemented with two stacks (in and out). enqueue pushes to in. dequeue pops from out; if out is empty, it first moves every element from in to out (one pop + one push each). Show dequeue is amortized O(1). Aggregate

Reveal answer

Key observation: each element is moved from in to out at most once in its lifetime. So across n operations, the total "transfer" work is bounded by the number of elements ever enqueued ≤ n.

Each element is touched a constant number of times total: 1 push to in, 1 pop from in, 1 push to out, 1 pop from out = 4 operations over its whole life.

Total work over n ops = O(n). Divide by n →

Amortized O(1) per operation

— even though a single dequeue that triggers a transfer can cost O(n).

14Use the accounting method for the two-stack queue above: assign charges so the transfer is prepaid. Accounting

Reveal answer

Charge: enqueue = 3, dequeue = 1.

Allocation for enqueue (3 coins): 1 pays the push onto in now; 2 are stored on the element to prepay its future pop from in and push onto out during a transfer.

dequeue (1 coin): pays the single pop from out.

Invariant: every element sitting in in carries 2 prepaid coins, exactly covering its eventual transfer. Balance never negative.

All charges constant → amortized O(1).

15A k-bit binary counter also supports reset (set all bits to 0, cost = number of 1-bits cleared). Does the amortized O(1)-per-operation bound still hold if we mix increments and resets? Explain. Accounting / tricky

Reveal answer

Yes, with the accounting method. Charge 2 per increment as before: 1 to set a bit to 1 now, 1 stored on that 1-bit to prepay clearing it later.

Why reset is free (amortized): every 1-bit in the counter was set by some earlier increment that already stored a coin on it. When reset clears those bits, the stored coins pay for all the clearing — reset is charged 0 and still never overdraws the balance.

Amortized O(1) per operation holds, even mixing increments and resets.

This is the classic example where the aggregate method struggles (a reset's cost depends on history), but the accounting method handles it cleanly — the prepaid credit idea does the work.
