How to approach pseudocode complexity

  • Loops: count how many times each runs. A loop 0..n is O(n). A loop where the counter multiplies (×2) or divides (/2) is O(log n).
  • Nested loops: multiply their counts. Watch for inner loops whose bound depends on the outer variable (often a sum → O(n²)).
  • Recursion: write T(n)=a·T(n/b)+f(n) and apply the Master Theorem, or sum the recursion tree.
  • Greedy/correctness: find a counterexample to disprove, or give an exchange argument to prove.

1What is the time complexity? pseudocode

total = 0
for i in 1..n:
    for j in 1..n:
        total = total + 1
Reveal answer & steps
Step 1. Outer loop runs n times.
Step 2. For each outer iteration, inner loop runs n times.
Step 3. Total iterations = n × n = n².

Θ(n²).

2What is the time complexity? Note the inner loop's bound. pseudocode

count = 0
for i in 1..n:
    for j in 1..i:        # note: j goes up to i, not n
        count = count + 1
Reveal answer & steps
Step 1. When i=1 inner runs 1 time; i=2 → 2 times; … i=n → n times.
Step 2. Total = 1+2+3+…+n = n(n+1)/2.
Step 3. Drop constants/lower terms: n(n+1)/2 = (n²+n)/2 → dominant term n².

Θ(n²).

A triangular loop is still O(n²) — it does half the work of a full nested loop, but constants don't change Big-O.

Reveal answer & steps
Step 1. j takes values 1, 2, 4, 8, … doubling each time.

5Determine the recurrence and time complexity. pseudocode

function f(n):
    if n <= 1: return 1
    return f(n-1) + f(n-1)
Reveal answer & steps
Step 1. Two recursive calls, each on size n−1, plus O(1) work.
Step 2. Recurrence: T(n) = 2T(n−1) + O(1).
Step 3. Each level doubles the number of calls: 1, 2, 4, …, 2ⁿ. This is NOT a Master-Theorem (n/b) form — it's a decrement recurrence.

Θ(2ⁿ) — exponential.

Trap: n−1 (subtract) grows very differently from n/2 (divide). Subtracting a constant → exponential; dividing → logarithmic depth.

6Determine the recurrence and time complexity. pseudocode

function g(n):
    if n <= 1: return
    g(n/2)
    for i in 1..n: print(i)    # O(n) work
Reveal answer & steps
Step 1. ONE recursive call on n/2, plus O(n) work. → a=1, b=2, f(n)=n.
Step 2. T(n) = T(n/2) + n.
Step 3. Recursion tree: work is n, then n/2, then n/4, … a decreasing geometric series summing to ~2n.

Θ(n).

Master Theorem check: c=log₂1=0, f(n)=n > n⁰ → Case 3 → Θ(n). ✓

7What is the SPACE complexity (extra memory)? pseudocode

function sum(arr, i):
    if i == length(arr): return 0
    return arr[i] + sum(arr, i+1)
Reveal answer & steps
Step 1. No extra data structures allocated.
Step 2. The recursion chain sum(0)→sum(1)→…→sum(n) is n calls deep, all on the stack before any returns.

Space = O(n)

(from the call stack). An iterative loop version would be O(1).

8This append doubles capacity when full. What is the AMORTIZED cost per append? pseudocode

function append(x):
    if size == capacity:
        newArr = allocate(2 * capacity)   # O(capacity)
        copy all elements to newArr
        capacity = 2 * capacity
    arr[size] = x
    size = size + 1
Reveal answer & steps
Step 1. Most appends are O(1) (just write). Occasionally a resize copies all elements, O(n).
Step 2. Aggregate over n appends: n writes + copies at sizes 1,2,4,…,n ≈ 2n copies. Total ≈ 3n.
Step 3. 3n / n = 3.

Amortized O(1) per append

(even though a single append can be O(n)).

9This greedy coin change takes the largest coin each time. For coins {1,3,4} and amount 6, is the result optimal? pseudocode

function makeChange(coins_desc, amount):
    count = 0
    for c in coins_desc:       # largest first
        while amount >= c:
            amount = amount - c
            count = count + 1
    return count
Reveal answer & steps
Step 1 — Trace. amount=6. Largest coin ≤ 6 is 4 → amount=2, count=1. Then coin 3 > 2, skip. Coin 1 → 1,1 → count=3.
Step 2 — Greedy result. 4+1+1 = 3 coins.
Step 3 — Optimal. 3+3 = 2 coins.

Not optimal. This single counterexample disproves greedy for the {1,3,4} system.

10This activity-selection greedy sorts by duration (shortest first). Prove it's incorrect with a counterexample. pseudocode

function selectActivities(acts):
    sort acts by (finish - start) ascending   # shortest duration first
    chosen = []
    for a in acts:
        if a compatible with all in chosen:
            chosen.add(a)
    return chosen
Reveal answer & steps
Step 1 — Build a counterexample. A=[1,5], B=[4,6], C=[6,10]. Durations: A=4, B=2, C=4.
Step 2 — Greedy picks shortest first = B[4,6]. B overlaps A (5>4) and touches C → blocks both. chosen = {B} → 1 activity.
Step 3 — Optimal. A[1,5] + C[6,10] → 2 activities.

Incorrect. Shortest-duration first is not optimal; only earliest-FINISH is provably optimal.

11This is binary search. How many iterations (comparisons of arr[mid]) does it take worst-case for n=16? pseudocode

lo = 0; hi = n - 1
while lo <= hi:
    mid = (lo + hi) / 2
    if arr[mid] == target: return mid

Reveal answer & steps

12Does this "find max" pseudocode work correctly for ALL integer arrays? If not, fix it. pseudocode

function findMax(arr):
    max = 0                 # <-- suspicious initial value
    for x in arr:
        if x > max: max = x
    return max
Reveal answer & steps
Step 1 — Spot the bug. max starts at 0. If every element is negative (e.g. [-5,-2,-9]), no x is > 0, so it wrongly returns 0.
Step 2 — Fix. Initialize max = arr[0] (and loop from index 1), or max = -infinity.

Not correct for all inputs — fails on all-negative arrays.

Time is still Θ(n) once fixed.

13What is the time complexity of this two-pointer loop (arr sorted)? pseudocode

lo = 0; hi = n - 1
while lo < hi:
    if arr[lo] + arr[hi] == target: return true
    if arr[lo] + arr[hi] < target: lo = lo + 1
    else: hi = hi - 1
return false
Reveal answer & steps
Step 1. Each iteration moves lo up OR hi down by 1 — the gap (hi−lo) shrinks by exactly 1 each time.
Step 2. Starting gap is n−1, so at most n−1 iterations.

Θ(n).

14Time complexity? The inner loop multiplies. pseudocode

for i in 1..n:
    j = i
    while j < n:
        j = j * 2
Reveal answer & steps
Step 1. Outer runs n times. For a given i, j goes i → 2i → 4i … until ≥ n, which is about log₂(n/i) steps.
Step 2. An upper bound: each inner loop is at most log₂n steps, so total ≤ n·log n.

O(n log n)

(a tighter sum of log(n/i) also gives O(n), but O(n log n) is the safe, commonly-accepted bound).

15Identify this algorithm, give its recurrence, time, and space. pseudocode

function sort(A):
    if length(A) <= 1: return A
    mid = length(A)/2
    L = sort(A[0..mid]); R = sort(A[mid..])
    return merge(L, R)      # merge is O(n), uses a temp array
Reveal answer & steps
Step 1. It's Merge Sort: 2 subproblems of size n/2 + O(n) merge. → T(n)=2T(n/2)+n.
Step 2 — Time. c=log₂2=1, f(n)=n=n^c → Case 2 → Θ(n log n).
Step 3 — Space. Temp merge array O(n) dominates the O(log n) stack → O(n).

16What is the EXPECTED number of iterations of this loop? pseudocode

repeat:
    x = random integer in [1..6]   # a die roll
until x == 6
Reveal answer & steps
Step 1. Each iteration "succeeds" (x==6) with probability p = 1/6, independently.
Step 2. This is a geometric distribution; expected trials to first success = 1/p.

E = 1/(1/6) = 6 iterations.

17Array of n elements, each independently set to 1 with probability 1/3. What is the expected value of count? pseudocode

count = 0

        count = count + 1
Reveal answer & steps
Step 1. Let Xᵢ = 1 if iteration i increments. E[Xᵢ] = Pr = 1/3.

E[count] = n/3.

18This stack's multipop can cost O(n). Using the accounting method, assign charges so each operation is amortized O(1). pseudocode

push(x):      stack.add(x)                 # real cost 1
multipop(k):  for _ in 1..min(k, size):    # real cost = items popped
                  stack.removeTop()
Reveal answer & steps
Step 1 — Charge. push = 2, multipop = 0.
Step 2 — Store credit. Of push's 2 coins, 1 pays the push now, 1 is saved on the pushed element as a "prepaid pop."
Step 3 — Invariant. Every element on the stack carries 1 coin; when multipop removes it, that coin pays for the pop. Credit never goes negative.

Amortized O(1) per operation.

19Explain why "the running time is O(n²)" and "the running time is Θ(n²)" are different claims. concept

Reveal answer & steps

O(n²) = upper bound only ("no worse than n²") — the true time could be smaller (e.g. actually n). Θ(n²) = tight bound ("grows exactly like n²", both upper and lower). Θ is the stronger, more precise claim; O is a guarantee ceiling.

20A deterministic Quick Sort uses the first element as pivot. Why is a RANDOM pivot preferred, and what does it change? concept

Reveal answer & steps

With a fixed first-element pivot, a sorted (or reverse-sorted) input forces lopsided partitions (n−1 and 0) every level → worst case Θ(n²). A random pivot means no specific input can reliably trigger that, so the EXPECTED time becomes O(n log n). The worst case Θ(n²) still exists but is astronomically unlikely. (Correctness is unchanged — it's a Las Vegas algorithm.)
